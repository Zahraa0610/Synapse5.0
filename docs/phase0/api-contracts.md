# Current API contracts

All routes below have /api prefix. Requests use JSON unless file parameters are specified, in which case multipart/form-data is required. Responses are JSON objects except authenticated file downloads. Existing module shapes remain compatible. Common error: {"error":"message"}; 400 invalid inputs, 401 missing/expired/revoked session, 403 scope/approval denied, 404 missing object, 409 duplicate/conflict, 413 request too large, 503 unavailable external provider.

Authentication: Authorization: Bearer <token>. Login/register return {token,user}; user includes active role, requested_role, verification_status and existing account fields. Tokens expire after eight hours and must match an unrevoked auth_sessions row. Old tokens without sid are invalid. Never infer authorization from requested_role.

Credential submission: POST /me/verification-file with multipart file and document_kind=identity|professional|practice (PDF/PNG/JPEG/WebP, matching signature, <=5MB) returns {user}. GET /me/credentials returns {credentials:[{id,filename,document_kind,status,review_note}]}. GET /credentials/<id>/file is owner/reviewer only. Review PATCH /users/<id>/verification accepts status pending|approved|rejected, optional note, and required shelter_id for coordinator approval. Returns {user}; approved activates the requested role. Self-review and peer Ministry activation return 403. Operator authorization remains outside public APIs. Queue includes private document IDs only for approved Ministry reviewers.

Clinical approval requires identity and professional documents; institutional roles require identity evidence.

## Endpoint inventory
Request keys, response constructors and related model names below are extracted from actual route functions, not a claim that every product workflow is complete. Any-auth endpoints also require object ownership/grants where specified in code. All active privileged roles require approved status; coordinators require assigned shelter. Return expressions show source-level shapes, including serializers whose fields are defined in domain.py and each route module. Phase 0 authentication/privacy routes were tested; broader product mutations are partial and require feature-specific validation.

## Proposed contracts (not implemented)

A real phone provider should own POST /auth/phone-code {phone} -> {challenge_id,expires_at} and POST /auth/phone-verify {challenge_id,code} -> {token,user}; both need provider-backed delivery, expiry, attempt limits and abuse protection. Today phone-code and phone login honestly return 503. Proposed role/permission and caregiver multi-user grants, organizations CRUD, audit events and emergency consent/revocation need reviewed schemas and explicit object-scoped routes in separate phases. Use feature-status.md for the supplied exact 57-feature map. For future modules, review proposed contracts before parallel implementation.

Public health endpoint: GET /api/health, no body/auth, returns {ok:true,name:"Ma'ak"}; no database tables required.
